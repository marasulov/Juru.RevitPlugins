# Задание бэкенду: согласование заданий на отверстия

Контракт — [OpeningsApi.md](OpeningsApi.md). Здесь только то, что нужно сделать на сервере, чтобы
работал уже написанный плагин, и то, как это проверить. Правила не пересказываются: у каждого пункта
ссылка на раздел контракта, он остаётся единственным источником.

Состояние на 2026-08-28: плагин отправляет и читает задания, ставит их в файле АР/КР, показывает
решения и умеет прорезать согласованное. Ниже — то, чего не хватает с серверной стороны.

## 1. `approvers` — с кем согласовывать (блокирует прорезание)

Раздел контракта: "С кем согласовывать".

Плагин уже присылает в `POST api/openings` поле `approvers` — `["ARC"]`, `["STR"]` или обе, минимум
одна. Нужно:

- принимать и хранить состав согласующих для заданий пачки;
- считать общий статус **только по этим дисциплинам**: если требуется одна АР, её `approved` даёт
  общий `approved`;
- возвращать `approvers` в `GET api/openings` рядом со `status`;
- при повторной отправке того же `taskKey` с другим составом — заменять требование и пересчитывать
  общий статус.

Почему это первым: на объекте, где КР не ведёт модель в Revit, согласования от КР не будет никогда.
Пока обязательны обе дисциплины, задание не доходит до `approved`, а плагин прорезает только
`approved` — то есть не прорезает ничего. Сейчас по объекту `Control_building` на сервере 55 заданий
`sent`, 4 `partiallyApproved`, 1 `rejected` и **ни одного** `approved`.

Проверка: отправить пачку с `approvers: ["ARC"]`, согласовать от АР через `POST api/openings/status`,
затем `GET api/openings` — у задания должно быть `"status": "approved"` и `"approvers": ["ARC"]`.

## 2. Повторная отправка удалённого ключа снимает пометку удаления

Разделы контракта: "Как задание адресуется", "Удалённые задания".

Плагин теперь возвращает пересозданным заданиям прежний `taskKey`: перед отправкой он спрашивает
`GET api/openings`, узнаёт задание по месту и типу отверстия и записывает найденный ключ в параметр
экземпляра. Поэтому ранее удалённый ключ может прийти снова — и это то же задание, а не новое.

Нужно: при получении `taskKey`, помеченного удалённым, снимать пометку. Решения при этом живут по
прежнему правилу — та же геометрия оставляет решение в силе, заметно другая сбрасывает в `sent`.

Проверка: удалить задание в модели, отправить полную пачку (ключ пропадёт → сервер помечает
удалённым), поставить задание заново на том же месте, отправить снова — в `GET api/openings` тот же
`taskKey` с `"deleted": false`.

## 3. Порог "заметно отличается" для сброса решений

Раздел контракта: "POST api/openings — выдача заданий".

Считает сервер. Раньше это было отложено с оговоркой "у инженерной стороны всё равно каждый прогон
даёт новый ключ" — оговорка больше не действует: расстановка двигает существующий экземпляр, а
пересозданное задание наследует ключ, поэтому повторная отправка того же ключа с другой геометрией
теперь обычное дело.

## 4. Openings API на 10.0.0.183

Плагин работает с адресом из своих настроек; у разработчика это `http://localhost:5000`, и там всё
отвечает. На `http://10.0.0.183`, который лежит в `ClashServer.json` рядом со сборкой (то есть у всех,
кто поставит MSI):

- `GET /api/openings?projectCode=Bash2&objectName=Control_building&discipline=HVC` → `200` и пустой
  массив;
- `GET /api/projects/1/objects` → только `Dormitory building`, объекта `Control_building` нет.

Нужно раскатать те же эндпоинты, что на localhost, и создавать объект при первой выгрузке заданий по
нему (или сказать, что объекты заводятся вручную — тогда плагин должен отличать "объекта нет" от
"заданий нет", и это уже задача плагина).

## 5. Карточка Асаны: состав согласующих

Раздел контракта: "Что сервер делает, получив выгрузку".

В сводке показывать, чьё согласование ждут: "ждём АР" и "ждём АР и КР" — разные состояния, по одному
числу `partiallyApproved` их не различить.
