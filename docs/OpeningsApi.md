# Задания на отверстия: обмен с сервером

Плагин `Juru.RevitPlugins.Openings` выдаёт задания на отверстия в файле ВИС и отправляет их на сервер,
а в файлах АР и КР показывает полученные задания и записывает решения по согласованию.
Ниже контракт, который нужно реализовать на бэкенде.

Адрес сервера — тот же, с которого ClashNavigator читает `api/projects`
(см. [ClashStatusUpdateApi.md](ClashStatusUpdateApi.md)), плюс новые эндпоинты `api/openings`.

## Как задание адресуется

Проект и объект определяются по имени файла Revit по стандарту наименования организации:
`Проект-Название_объекта-Дисциплина-vNN.rvt`, разбор — `Juru.RevitPlugins.Core.FileNaming.RevitFileNameInfo`.
Дисциплины `WSS`, `ELE`, `HVC` выдают задания; `ARC` и `STR` их принимают.

Ключ задания — `taskKey`: `UniqueId` экземпляра семейства задания в файле ВИС. Он стабилен между
сеансами, переживает синхронизацию и виден из связи, поэтому по нему сходятся запись в модели ВИС,
запись на сервере и чистовое отверстие в АР/КР. Пересозданное вручную задание получает новый ключ —
это честно новое задание.

## Два независимых статуса

Не путать, это разные вещи и хранятся они по-разному.

**Техническое состояние** задания вычисляется по геометрии при каждом открытии окна и на сервере
**не хранится**: новое, частично выполненное, выполненное, нет пересечения, неактуальное. Хранить его
бессмысленно — оно меняется от любой правки модели без участия человека.

**Решение по согласованию** принимает человек, и его хранит сервер. Именно за этим плагину нужен
сервер: модель Revit не помнит, кто и почему отклонил задание.

| Значение   | Смысл                                       | Кто ставит |
|------------|---------------------------------------------|------------|
| `sent`     | Задание выдано инженером и ждёт рассмотрения | ВИС        |
| `approved` | Задание принято                              | АР или КР  |
| `rejected` | Задание отклонено, причина в `comment`       | АР или КР  |

## POST api/openings — выдача заданий

Инженер нажимает кнопку отправки, плагин отправляет всё выданное одной пачкой.

```
POST {baseUrl}/api/openings
Content-Type: application/json; charset=utf-8
```

```json
{
  "projectCode": "BASH2",
  "objectName": "Корпус_1",
  "discipline": "HVC",
  "sentBy": "JURU\\y.marasulov",
  "sentByDisplayName": "Yusuf Marasulov",
  "sentAt": "2026-08-18T07:15:42.1234567Z",
  "source": "Revit Openings",
  "items": [
    {
      "taskKey": "0f2c1a44-8f1e-4c2a-9a41-6c1b2d3e4f50-000a1b2c",
      "openingType": "WallRectangle",
      "location": { "x": 12.5, "y": -3.2, "z": 8.15 },
      "widthMm": 350,
      "heightMm": 250,
      "diameterMm": null,
      "thicknessMm": 200,
      "mepSystem": "П1",
      "mepElementKind": "RectangleDuct",
      "hostKind": "Wall",
      "levelName": "01 этаж",
      "elevationFromZeroMm": 3150,
      "description": "",
      "manuallyPlaced": false
    }
  ]
}
```

| Поле                          | Тип             | Описание |
|-------------------------------|-----------------|----------|
| `projectCode`, `objectName`   | string          | Из имени файла ВИС. Сервер сопоставляет их со своими проектом и объектом так же, как для коллизий. |
| `discipline`                  | string          | `WSS`, `ELE` или `HVC` — дисциплина файла, выдавшего задания. |
| `sentBy`                      | string          | Учётная запись Windows, `DOMAIN\user`. Не имя пользователя Autodesk. |
| `sentByDisplayName`           | string          | Имя сотрудника из Windows — то, что нужно показывать в интерфейсах. |
| `sentAt`                      | string ISO 8601 | Время на машине пользователя, **UTC**. |
| `items`                       | array           | Выданные задания, минимум одно. Пачка может быть и в одно задание, и в несколько тысяч. |
| `items[].taskKey`             | string          | Ключ задания, см. выше. Уникален в пределах объекта и дисциплины. |
| `items[].openingType`         | string          | `WallRound`, `WallRectangle`, `FloorRound`, `FloorRectangle`. |
| `items[].location`            | object          | Точка вставки в координатах проекта, в **метрах**. |
| `items[].widthMm` и далее     | number или null | Габариты в мм. У круглых заполнен `diameterMm`, у прямоугольных — `widthMm` и `heightMm`. |
| `items[].thicknessMm`         | number          | Толщина конструкции в месте прохода. |
| `items[].mepSystem`           | string          | Имя инженерной системы. |
| `items[].mepElementKind`      | string          | `Pipe`, `RoundDuct`, `RectangleDuct`, `CableTray`, `Conduit`. |
| `items[].hostKind`            | string          | `Wall` или `Floor`. |
| `items[].elevationFromZeroMm` | number          | Отметка низа отверстия от нуля здания. |
| `items[].manuallyPlaced`      | bool            | Задание размещено вручную, а не найдено алгоритмом. Такие не перезаписываются авторасстановкой. |

Повторная отправка того же `taskKey` — это **обновление**, а не новая запись: инженер правит трассу и
выдаёт задания снова. Габариты и точку нужно перезаписать, а решение по согласованию — сохранить, но
пометить, что задание изменилось после согласования (см. `changedAfterApproval` ниже).

Ответ `200 OK`:

```json
{ "accepted": 128, "updated": 12, "failed": [] }
```

`failed[]` — элементы вида `{ "taskKey": "...", "message": "..." }`. Плагин показывает `message`
пользователю и считает эти задания неотправленными, поэтому повтор придёт только по ним.

## GET api/openings — полученные задания

Файл АР или КР запрашивает задания своего объекта. Дисциплина в запросе — **не** дисциплина
открытого файла, а те, чьи задания нужно показать.

```
GET {baseUrl}/api/openings?projectCode=BASH2&objectName=Корпус_1&discipline=HVC&discipline=WSS
```

`discipline` можно не указывать — тогда возвращаются задания всех дисциплин объекта.

```json
[
  {
    "taskKey": "0f2c1a44-8f1e-4c2a-9a41-6c1b2d3e4f50-000a1b2c",
    "openingType": "WallRectangle",
    "widthMm": 350,
    "heightMm": 250,
    "diameterMm": null,
    "mepSystem": "П1",
    "discipline": "HVC",
    "sentBy": "JURU\\y.marasulov",
    "sentByDisplayName": "Yusuf Marasulov",
    "sentAt": "2026-08-18T07:15:42Z",
    "approvalStatus": "approved",
    "decidedBy": "JURU\\a.ivanov",
    "decidedByDisplayName": "Alexey Ivanov",
    "decidedAt": "2026-08-18T09:02:11Z",
    "comment": "",
    "changedAfterApproval": false
  }
]
```

Геометрию плагин берёт из самой связи, а не отсюда: связь всегда свежее сервера. С сервера нужны
`approvalStatus`, автор решения, время и комментарий — то, чего в модели нет. Габариты в ответе нужны
только чтобы показать, **каким** задание было на момент согласования, если оно с тех пор изменилось.

`changedAfterApproval` сервер выставляет сам, когда `POST api/openings` перезаписал габариты или
точку задания, у которого уже стоял `approved`. Плагин показывает такие задания отдельно: архитектор
согласовал одно, а в модели теперь другое.

## POST api/openings/status — решения по согласованию

Устроено так же, как `api/clashes/status`: решения копятся в окне и уходят одной пачкой по кнопке
сохранения, потому что HTTP-вызов идёт в потоке интерфейса.

```json
{
  "changedBy": "JURU\\a.ivanov",
  "changedByDisplayName": "Alexey Ivanov",
  "changedAt": "2026-08-18T09:02:11.1234567Z",
  "source": "Revit Openings",
  "items": [
    { "taskKey": "0f2c1a44-8f1e-4c2a-9a41-6c1b2d3e4f50-000a1b2c", "status": "approved", "comment": "" },
    { "taskKey": "7b3d9e55-1c2d-4e3f-8a90-1b2c3d4e5f60-000c4d5e", "status": "rejected", "comment": "Попадает в колонну, сместите на 400 мм" }
  ]
}
```

У `rejected` комментарий обязателен — плагин не даст отклонить задание без причины. Ответ и обработка
ошибок — как у `api/clashes/status`: `{ "updated": N, "failed": [...] }`, непустой `failed` плагин
показывает пользователю и оставляет решения непереданными до следующего сохранения.

## Что нужно сохранить в базе

1. Задания с их габаритами, точкой и авторством выдачи, с уникальностью по `taskKey` внутри объекта.
2. Решение по согласованию: статус, автор — и `changedBy`, и `changedByDisplayName`, — время, комментарий.
3. Историю: по строке на каждое изменение статуса и на каждую перевыдачу задания. Плагин её не читает,
   но без неё не разобрать, почему отверстие в модели не совпадает с тем, что согласовывали.

Техническое состояние задания (выполнено, неактуально и прочее) на сервер не отправляется и в базе
не хранится: оно вычисляется в Ревите по геометрии.
