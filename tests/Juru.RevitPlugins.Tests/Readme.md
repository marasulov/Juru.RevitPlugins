# Тесты

```bash
dotnet test tests/Juru.RevitPlugins.Tests/Juru.RevitPlugins.Tests.csproj -c Debug.R24
```

Прогоняются и в CI (`.github/workflows/Compile.yml`) после сборки решения.

## Что здесь покрыто

Логика из `Juru.RevitPlugins.Core/FileNaming` - разбор имени файла по стандарту наименования и
сопоставление имён объекта с базой сервера. Выбрано не случайно: в этих двух файлах нет ни одной
ссылки на Revit API, и они же дважды ломались в проде, причём молча - разбор возвращал `false`, а
вызывающий код считал, что подходящих связей просто нет (Changelog 0.0.19 и 0.0.20). Случаи из тех
разборов лежат в тестах отдельными фактами.

## Чего здесь нет и почему

Тестами такого рода **нельзя** покрыть код, у которого в полях лежат типы Revit API -
`ClashModel`, `ElementModel`, всё вокруг `Filter` и провайдеров параметров. Причина не в
архитектуре плагина, а в самих сборках Ревита:

- из NuGet-пакетов `Nice3point.Revit.Api.*` приходит эталонная сборка (`ref/`) - без тел методов.
  С ней собирается, но не выполняется;
- настоящая `RevitAPI.dll` из установленного Ревита - смешанная сборка C++/CLI. Она подтягивает
  нативные библиотеки Ревита и вне его процесса не загружается: `Could not load file or assembly
  'RevitAPI.DLL' or one of its dependencies`.

Загрузить типы Ревита достаточно один раз - дальше падает всё, что их касается, даже если сама
проверяемая логика чисто арифметическая. Поэтому `ClashesMarker.CountAdded`/`CountGone`
(сопоставление прогонов проверки) здесь не проверяются, хотя логика в них ровно та, что просится
в тест.

Правильный инструмент для этого - тесты, выполняющиеся **внутри** Ревита
(`Nice3point.TUnit.Revit`): они запускают Ревит, получают настоящий `Document` и работают с
живым API. Это отдельная установка и отдельный прогон, не для CI - имеет смысл заводить, когда
понадобится покрыть сам поиск коллизий, а не только логику вокруг него.
